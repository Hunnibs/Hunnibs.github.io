# [Troubleshooting] 127.0.0.1 로그 발생 원인 추적 및 모니터링 봇 차단
## 1\. 현상: 의문의 '127.0.0.1' 방문 기록 발생
시스템 접근 IP 로그를 모니터링하던 중, 실제 사용자 IP가 아닌 127.0.0.1로 저장된 기록들을 발견했다.
SQL

### -- 기존 로그 저장 로직
~~~
NVL(#SESS_IP#, (SELECT SYS_CONTEXT ('USERENV', 'IP_ADDRESS') FROM DUAL))
~~~
세션에 IP 정보가 없을 경우 DB의 SYS_CONTEXT를 통해 직접 IP를 따오도록 설계되어 있었으나, 이 과정에서 서버 자기 자신을 가리키는 **Loopback Address(127.0.0.1)**가 찍힌 것으로 추정.

## 2\. 원인 분석: 누가 호출했는가?
처음에는 내부 스케줄러나 배치 작업이 원인이라 생각했으나, 범인은 외부에 있었습니다. **JEUS WAS의 Access Log**를 분석한 결과, 외부 모니터링 서비스와 봇들이 지속적으로 GET 요청을 보내고 있음을 확인했습니다.
> **왜 127.0.0.1인가?**    
보통 로컬에서 서버가 돌아가거나, 특정 헬스체크(Health Check) 봇이 서버 내부망을 통해 접근할 경우 혹은 DB와 WAS가 같은 물리 서버에 있어 SYS_CONTEXT가 호출 주체를 로컬로 인식할 때 발생합니다. 이번 사례는 세션 정보가 없는 비정상적 접근(봇)이 DB 쿼리를 직접 타면서 발생한 로깅 오류였습니다.

## 3. 해결책 1: 검색엔진 및 봇 접근 제어 (robots.txt)
무분별한 크롤링과 모니터링 봇의 접근을 제어하기 위해 robots.txt 설정을 추가했습니다.
**robots.txt**
~~~
User-agent: *
Disallow: /
Allow: /$
~~~
* **Disallow: /** : 모든 페이지의 수집을 거부합니다.
* **Allow: /$** : 메인 페이지(root)만 수집을 허용하여 검색 엔진에 최소한의 노출은 유지합니다.

> ⠀**💡 주의:** robots.txt는 "출입 금지" 표지판과 같습니다. 선의의 봇(구글, 네이버 등)은 이 규칙을 지키지만, 악의적인 공격 봇은 이를 무시하고 들어올 수 있으므로 물리적인 방화벽이나 인터셉터(Interceptor) 처리가 병행되어야 합니다.
